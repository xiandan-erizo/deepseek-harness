# Agent Note: 历史记录分页限制浏览器回放，同时不切分消息

Status: implemented

[English](2026-08-04-large-history-pagination-call-stack.md) | 中文

## 问题

一条已定稿的 assistant 消息可以通过 `sourceEventSeqs` 引用数十万个流式分片。历史记录分页使用 `Math.min(event.seq, ...sourceEventSeqs)` 查找消息组的首个事件，因此，有效会话可能超出 JavaScript 引擎的函数参数数量上限，导致 `session.history` 以 HTTP 500 失败。即使不抛出这个异常，只按追加来源的消息计数也会让一个尾页携带数百条原始分片和工具事件，使浏览器回放开销大到无法打开对话。

## 决策

分页逻辑逐项扫描 `sourceEventSeqs`，每次使用一个元素更新最早的序号。网关配置为历史页提供默认交互式回放上限：最多 128 个原始事件，最多 128 KiB 序列化原始事件数据，以及宿主计算出的工具 view 加入响应后最多 128 KiB 序列化 `HistoryEntry` 数据。单个派生 view 超过最终条目上限时会省略 view 而保留其持久事件。请求的消息页超过其余任一上限时，分页会推进到下一整个消息组，直到后缀满足上限。最新的一整个已定稿消息组可能自身超过原始事件上限，因为切断其溯源会让回放不完整。

响应仍使用连续原始事件区间，并在回放上限推进起点时报告 `hasMore`。`maxMessages` 仍是最大值而非承诺值，所以有界页面返回的消息数可以少于请求值。

回归覆盖会拒绝多参数取最小值、保留每个溯源事件与其已定稿消息，并证明分片密集的尾页会先按完整消息边界推进，再交给浏览器；同时覆盖 view 大于原始工具结果的 presenter。

## 考虑过的替代方案

- **提高 JavaScript 栈或参数上限**：不予采纳，因为该上限取决于引擎和部署环境，而且数组展开仍会让有效历史记录受制于无关的运行时上限。
- **在分页时截断 `sourceEventSeqs`**：不予采纳，因为这可能会从消息中间切分页面，破坏回放分组。
- **只按消息计数**：不予采纳，因为流式分片和工具事件不消耗消息配额，无法限制浏览器工作量。
- **在提供方边界限制流式分片数量**：不予采纳，因为提供方可能会合理地产生长流，而分页必须处理每一种有效的会话表示。

## 后果

- 大型溯源数组不再仅因长度而使历史记录分页抛出异常。
- 普通页面受到原始事件数量、序列化事件字节数和序列化渲染条目字节数限制，避免高分片数量或 presenter view 形成无界的浏览器首屏回放。
- 调用方可能收到少于请求上限的消息；单条超大的已定稿消息仍必须作为一个整体回放。
